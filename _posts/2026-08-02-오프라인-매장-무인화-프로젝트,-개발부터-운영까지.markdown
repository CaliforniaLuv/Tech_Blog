올해 전반기, PO님과 개발 팀장님께서 주간 회의를 통해 대규모 프로젝트를 진행할 예정이라는 소식을 공유해 주셨다.

프로젝트의 핵심은 기존 오프라인 스크린 골프 매장을 모두 무인화 시스템으로 전환하는 것이었다.

프로젝트 내용을 듣자마자 가장 먼저 든 생각은 "IoT 기반 기술에 대한 이해가 많이 필요하겠는데?" 였다.
전공이 전자공학이긴 하지만 IoT 분야를 다룬 지는 벌써 4~5년이 지났다. 이전 회사에서 인턴으로 근무할
당시 잠시 관련 개발을 맡았던 [경험](https://www.imaeil.com/page/view/2021020312444739072)이 있었지만, 이후에는 줄곧 IT 서비스 개발 업무만 해왔기 때문이다.

IT와 IoT에 대한 다양한 지식이 복합적으로 요구될 것이라는 생각에, 벌써부터 걱정이 앞서는 프로젝트는 정말 오랜만이었다.

한동안 서랍 속에 넣어 두었던 걱정인형을 다시 내 침대 옆에 나둘 만큼, 개인적으로 많은 우려가 있었던 프로젝트였다.
이번 글에서는 몇 개월 동안 프로젝트를 진행하며 겪었던 과정과 시행착오, 그리고 그 속에서 얻은 경험을 기록해 보려 한다.

# 초기 고민과 방향성

## 1-1 무인화 매장 진짜 괜찮은게 맞을까..?

![골프 이미지1](https://californialuv.github.io/Tech_Blog/images/2026-08-02/royal-golf.jpeg)

회사에서 운영 중인 스크린 골프 매장은 일반적인 스크린 골프와는 몇 가지 차별점이 있다.
가장 큰 특징은 고급스러운 인테리어와 고객을 VIP처럼 응대하는 프리미엄 서비스다. 이러한 차별화된 경험 덕분에 꾸준히 매장을 찾는 고객층이 형성되어 있다.
골프는 비교적 프리미엄 레저 스포츠로 인식되는 만큼, 이러한 고급스러운 공간과 서비스는 매장의 경쟁력을 높이는 중요한 요소이다.

그런데 갑자기 무인화로 바뀌고 기존 매장의 매니저들은 오전 시간대에만 운영한다라.. 분명 타격이 있을 것이다.

프로젝트를 처음 접했을 때 가장 먼저 떠올랐던 걱정은 크게 네 가지였다.

첫 번째 고객 경험, 고객이 직접 키오스크와 패드를 이용해야 하는 환경에서는 기존에 제공되던 VIP 서비스의 느낌이 많이 줄어든다.

두 번째 이용이 끝난 뒤의 운영 방식, 골프 이용을 마친 고객이 다음 예약을 위해 직접 골프공을 정리해야 하는 상황이 발생한다면, 귀찮음과 불편함을 동시에 느낀다.

세 번째 기존 고객들의 적응 문제, 오랫동안 직원의 안내를 받으며 이용하던 매장이 갑자기 무인화된다면, 익숙한 고객일수록 많이 당황하거나 이용하기 어려워할 것이다.

마지막 네 번째 비용과 매출, 단기적으로는 매니저 인력을 줄여 인건비를 절감할 수 있겠지만, 장기적으로 고객 경험이 저하되어 매출에 영향을 미치지는 않을지 우려가 들었다.

결국 우리 매장 서비스는 '사치스러움'이 가장 큰 무기였는데 무인화는 '가성비'라는 이미지로 뒤바뀌게 될 것이다.
뭐 근데,, 이런 걱정들을 백날 수백 번 해봤자 나 같은 말단 직원이 건의하는 건 크게 영향도 없을 것 같다.

임원분들은 나보다 더 넓은 관점에서 사업의 방향성과 목표를 바라보고 있겠지..? 어쩌면 내가 현장에서 보이는
근시적인 변화만을 바라보며 걱정하고 있는 것일 수도 있다는 생각이 들기도 하다.

결국 내가 할 수 있는 일은 프로젝트의 방향을 의심하는 것이 아니라,
정해진 목표 안에서 오프라인 매장 무인화 서비스 만들기 위해 최선을 다하는 것이라고 생각하며 다시 개발에 집중하기로 했다.

## 1-2 웹앱 기반으로 갈까? 네이티브로 갈까?

![비교](https://californialuv.github.io/Tech_Blog/images/2026-08-02/versus.png)

다행히 내가 맡게 된 역할은 IoT 시스템과 연동해 실내 타석 룸의 TV, PC, 출입문을 제어하는 것이 아니라, 
키오스크와 패드를 통해 고객이 타석을 현장 예약하고 이용을 연장할 수 있는 __애플리케이션__ 과 매장 각 룸의 실시간 예약 현황을 보여주는 __DID(Digital Information Display)__ 화면을 개발하는 것이었다.

DID는 직영점 매장에 따라 각 룸의 정보를 대시보드 형태로 보여주면 됐기 때문에 React를 활용해 화면을 구현하는 방향으로 비교적 쉽게 기술 스택을 구성할 수 있었다.

하지만 실제 키오스크, 패드에 설치해야 하는 현장 예약 앱은 달랐다. 어떤 기술 스택을 선택하고, 디바이스 기기 환경에 맞게 어떻게 구성할지부터 고민할 부분이 많았다.

매장에 설치되는 키오스크와 패드(태블릿)는 Android 기반이며 벤더 업체에서 제공하는 장비를 사용했고, 결제 시스템은 [KICC(한국정보통신주식회사)](https://www.kicc.co.kr/) 결제 리더기를 연동하는 구조다.
가장 먼저 고민한 부분은 어떤 기술 스택을 기반으로 애플리케이션을 개발할 것인가 였는데, 프로젝트는 매주 개발 현황을 공유해야 할 만큼 일정이 빠듯했으며
네이티브 앱으로 개발하는 방법도 고려했지만, 당시 나에게는 개발 경험이 부족해 일정 리스크가 클 것 같았다.

결국 기존 예약 서비스에서 사용하던 __모바일 웹앱(React framework + Native App Wrapper)__ 구조를 그대로 활용하기로 결정했다. 이미 검증된 구조를 재사용하면 개발 속도를 높일 수 있었고,
기존 디자인 시스템을 통해 UI도 상당 부분 재활용할 수 있었다. 무엇보다 기능을 빠르게 구현하여 프로젝트 일정을 맞추는 데에도 가장 적합한 선택이라고 판단했다.

React SPA 기반 웹 애플리케이션을 Native App Wrapper로 감싸는 방식으로 React Native와 Capacitor 중 어떤 기술을 선택할지 비교·분석해 보았다.

![분석표](https://californialuv.github.io/Tech_Blog/images/2026-08-02/analysis-table_1.png)

위 토대로 어느 환경이 더 현명할 지 고려한 결과, 나의 최종 선택은 __Capacitor__ 였다.

- __React Native의 장점을 활용하기 어려운 프로젝트__ , React Native는 다양한 모바일 UI 라이브러리와 생태계를 갖추고 있지만, 이번 프로젝트는 화면을 모두 Next.js로 구현하는 구조다.
  따라서 React Native의 UI 생태계를 활용할 일이 거의 없고, 오히려 웹 기술을 그대로 유지하면서 필요한 네이티브 기능만 사용할 수 있는 Capacitor가 더 적합했다.
- __웹과 네이티브 간 통신 구조가 더 단순__ , React Native는 웹뷰를 사용할 경우 Web → React Native → Native SDK(카메라, 결제 리더기 등)를 거쳐야 하지만, Capacitor는 Web → Native SDK 형태로 플러그인을 직접 호출할 수 있다.
  통신 경로가 단순한 만큼 브리지 코드가 줄어들고 유지보수 측면에서도 유리하다고 판단했다.
- __이전 프로젝트 경험 영향__ ,  이전 예약 서비스 웹앱을 개발할 당시에는 스마트폰의 네이티브 기능을 사용할 때마다 postMessage를 이용해 웹(Next.js)과 네이티브 코드(React Native) 사이의 브리지 로직을 번거롭게 매번 구현해야 했다.
  Capacitor는 이러한 부분을 플러그인 API로 상당 부분 축소해 주기 때문에 개발 생산성을 높일 수 있을 것으로 기대했다.

<br>

나에겐 웹 애플리케이션과 네이티브 SDK를 얼마나 간결하고 안정적으로 연결할 수 있느냐가 더 중요했기에 Capacitor 특성이 더 적합하다고 느껴졌다.

### 하나의 앱으로 두 디바이스 환경 대응하기

키오스크와 패드, 두 환경에 맞춰 앱을 어떻게 구성할지 고민했다.

두 환경을 각각 별도의 앱으로 개발한다면 작업량이 상당히 많아질 것으로 예상됐다. 현장 예약, 이용권 구매, 사전 예약 등
주요 기능의 구현 방식이 대부분 유사했기 때문에, 별도의 앱으로 나누는 것은 불필요하게 개발 공수를 늘리는 결과가 될 수 있었다.

여러 방안을 숙고한 끝에 __하나의 앱에서 키오스크와 패드 환경을 모두 지원하는 방식__ 으로 방향을 잡았다.

웹뷰 기반으로 개발하는 구조였기 때문에 URL의 path를 '/kiosk', '/pad' 형태로 역할 분리하면 하나의 프로젝트 안에서
각 환경을 명확하게 구분하면서도 공통 기능은 재사용할 수 있어 관리하기 편리하다고 판단했다.
또한 키오스크와 패드는 화면 크기와 해상도가 서로 달랐기 때문에, 각 path에 해당하는 __최상위 layout__ 에서
환경별 스케일링 설정을 적용하여 디바이스 특성에 맞게 화면을 구성했다.

### 예약 앱과 kicc 결제 앱 간 App to App 연동

이번 프로젝트에서 가장 어려웠던 부분은 결제 연동이었다.

Capacitor 브릿지 구현을 위해 Java를 사용해야 했는데, 학부 시절 이후 거의 다뤄보지 않아 문법과 구조를 다시 익히는 데 시간이 꽤 걸렸다.
다행히 AI의 도움을 받아 Java 문법과 브릿지 구현 방식에 대해 수시로 질문하며 부족한 부분을 보완했고, 이를 바탕으로 내가 만든 앱과 KICC 결제 앱을 연동하는 방식을 구현했다.

키오스크와 패드에는 KICC 결제 앱(EasyCardA)이 함께 설치되어 있다. 카드 리더기 제어는 전부 결제 앱이 담당하므로,
우리 앱은 결제 시점에 결제 앱을 호출하고 승인 결과만 돌려받으면 된다. SDK를 붙이는 방식이 아니라 Android의 [Intent](https://developer.android.com/guide/components/intents-filters?hl=ko)를 이용한 App to App 방식이다.

{% highlight java %}

// 결제 앱의 결제 Activity를 명시적 Intent로 호출
Intent intent = new Intent();
intent.setClassName(PAYMENT_APP_PACKAGE, PAYMENT_ACTIVITY);
intent.putExtra(/* 거래 유형, 금액 등 연동 규격 파라미터 */);
startActivityForResult(call, intent, "paymentResult");

{% endhighlight %}

React(웹뷰)에서 이 네이티브 코드를 부를 수 있도록 Capacitor 커스텀 플러그인으로 감쌌고, 결제 앱이 돌려주는 응답의 결과 코드로 승인 성공 여부를 판정한다.

{% highlight js %}

// lib/native/kiccPayment.ts
export interface KiccPaymentPlugin {
  startPayment(input: { amount: number; tranNo: string }): Promise<{
    approved: boolean; // 결과 코드 기반 승인 여부
    raw: Record<string, string>; // 결제 앱 응답 원본 (승인번호 등)
  }>;
}
const KiccPayment = registerPlugin<KiccPaymentPlugin>("KiccPayment");

// src/paymentContainer.tsx
const van = await KiccPayment.startPayment({ amount, tranNo });
if (!van.approved) throw { kind: "DECLINED" };
// van.raw의 승인 정보로 서버 확정 진행

{% endhighlight %}

<br>

다만 Intent만 쏜다고 바로 동작하지는 않았고, 두 가지 설정이 더 필요했다.

1. 패키지 가시성(Android 11+) — 매니페스트에 <queries>로 결제 앱 패키지를 선언해야 상대 앱을 찾을 수 있다.

{% highlight js %}

  <!-- KICC EasyCardA 앱-투-앱 호출용(Android 11+ 패키지 가시성). -->
    <queries>
        <package android:name="kr.co.kicc.easycarda" />
    </queries>

{% endhighlight %}

2. 키오스크 잠금 모드 화이트리스트 — 키오스크는 __Lock Task Mode__ 로 잠겨 있어 외부 앱 실행이 차단되는데, 결제 앱을 화이트리스트에 등록해야 결제 화면이 뜬다.

{% highlight java %}

dpm.setLockTaskPackages(admin, new String[]{getPackageName(), KICC_PACKAGE});

{% endhighlight %}

### 카드 결제 VAN 승인시 위험 부분 발견

![결제 플로우차트](https://californialuv.github.io/Tech_Blog/images/2026-08-02/payment-flow.png)
*결제 진행 흐름도*
<br>

confirm API 완료 처리 중 만약 에러(네트워크 끊김, 다른 고객이 가로챔)가 발생하게 되면 다시 결제 버튼을 눌러 이용자가 __중복 결제__ 를 하게 되는 크리티컬한 버그를 발견하였다.

중복 결제 시나리오

```
1. 고객이 카드를 긁음 → startPayment → VAN 승인 성공 → 1차 출금 완료
2. 이어서 confirm 호출 → 하지만 네트워크 끊킴 / 서버 타임아웃 / 5xx로 실패
3. "결제 실패" 안내
4. 다시 결제하기 재시도 → prepare → startPayment 또 호출 → VAN 승인 -> 2차 출금 발생
5. 결제 금액 두 번 청구
```

<br>

테스트 중 confirm API 단계에 일부러 네트워크 오류를 발생시켜 해당 상황을 재현해 보았다. 
결제 플로우가 처음부터 다시 진행 되면서 카드 승인이 한 번 더 발생했다. 즉, 35,000원짜리 결제를 재시도했을 뿐인데 
고객의 카드에는 70,000원이 승인되는 문제가 발생할 수 있는 것이다.

처음에는 confirm API 과정에 에러가 발생될 경우, APP to APP 방식을 통해 자동 VAN 취소를 하는 방향으로 구현을 생각했다.

KICC EasyCardA APP에서 제공된 파리미터 메뉴얼에는 아래와 같이 승인 취소를 구현할 수 있었다.

1. 당일취소/전일취소(승인번호)
2. 직전거래통신취소(망취소)

위와 같은 결제 오류 상황에서는 2번 '직전거래통신취소' 방식이 적합하였지만 매장에서는 키오스크와 패드가 하나의 단말기 번호를 공유하고 있기 때문에 문제가 발생할 수 있었다. 
키오스크에서 결제 오류가 발생한 시점과 패드에서 정상 결제가 처리된 시점이 근접할 경우, 결제 취소 과정에서 어떤 거래를 취소해야 하는지 
정확하게 구분하기 어려워 패드에서 정상 처리된 결제가 잘못 환불되는 문제가 발생할 수 있다.

그래서 2번 방식 대신 1번 '당일취소/전일취소' 방식을 적용하고, 해당 방식으로 자동 환불이 정상적으로 처리되는지 테스트를 진행해보았다.


```
[결제하기 클릭 — 단 한 번]
│
├─ prepare API
├─ KICC VAN 승인 (카드 리더 삽입) ← 카드 넣는 건 여기 딱 1회
│→ 승인정보를 ref에 저장
│
├─ confirm API 최초 요청
│   실패(애매)
├─ confirm API 요청 재시도
│   실패 → 더 이상 재시도 안 함
└─ VAN 취소(D4) → 환불
```

<br>

위 과정은 카드 결제에서는 문제가 없지만 키오스크인 경우 바코드 센서를 통해 QR 결제 진행시 큰 문제가 있다.
카드인 경우 리더기 투입구에 계속 꽂힌 상태로 나두면 되지만 QR 인증을 할 경우, 바코드 센서에 최소 6~7초 간 계속 스마트폰을 갖다 대야 자동 환불이 된다. 
그 어떤 사용자가 QR을 저렇게 절대 사용하지 않을 거라고 생각을 했다.

... 아무리 봐도 벤더 업체가 판매한 키오스크가 이상하다고 느껴졌다.

```
PG 결제도 아니고 VAN 결제인데 바코드 결제 센서가 키오스크에 왜 장착 되어 있는건데 -.-
```

<br>

PG는 온라인 결제를 기반으로 하기 때문에 환불 처리가 비교적 자유로운 반면, 현재 키오스크와 패드에서 사용하는 KICC VAN 결제 시스템은 실물 카드나 QR을 다시 제시해야 환불할 수 있는 구조였다.
따라서 VAN 결제 방식에서는 환불을 위해 카드나 바코드 리더기를 직접 거쳐야 했고, App-to-App 연동만으로 자동 환불을 처리하는 데에는 여러 제약이 있었다.

결국 __사용자 행동에 따라 오류가 제각각__ 이므로 자동 환불은 안정적 대안이 되지 못한다는 점을 고려하여 위 작업 과정들은 모두 전면취소 하였다.

다른 방안으로는 VAN 승인 결과를 __Ref__ 참조 객체에 저장해두고, confirm API 요청 과정에서 오류가 발생해 결제를 재시도하는 경우 __카드 재승인 없이 confirm API 과정만 다시 수행__ 하도록 구현했다. 
이후에도 API 오류가 발생하면 사용자에게 문의를 안내하는 모달을 노출하도록 처리된다.

{% highlight js %}

const approvedRef = useRef<Approved | null>(null); // VAN 승인 캐시(재시도 시 재사용)

const pay = async (params: Params) => {
  // 1) 승인 확보 — 최초 1회만 카드 출금. 재시도면 이 블록을 통째로 건너뛴다.
  if (!approvedRef.current) {
    const { amount, context } = await config.prepare(params);
    const van = await KiccPayment.startPayment({ amount, tranNo });
    if (!van.approved) throw { kind: "DECLINED" };
    approvedRef.current = { vanApproval: normalizeVanApproval(van.raw), amount, context };
  }
  // 2) 확정 — 재시도 시 여기만 반복된다(이미 출금됐으므로 confirm만 재수행).
  return config.confirm({ ...approvedRef.current, params });
};

{% endhighlight %}

<br>

개선 후 결제 시나리오

```
1. 결제 화면에 에러 실패 되었다는 문구 발생
2. 결제 버튼 다시 누름
3. prepare API, kicc 결제 승인 모두 건너가고 바로 confirm 과정 재시도
4. confirm 에러 또 다시 발생
5. 관계자 문의 모달 안내 
```

<br>

사실 위와 같은 에러 상황이 실제로 발생할 가능성은 높지 않다. 하지만 결제 과정에서 작은 오류 하나만 발생해도 
이용자에게 금전적인 피해로 이어질 수 있기 때문에 발생 가능한 예외 상황까지 최대한 고려해 방어 로직을 마련할 필요가 있었다.

## 2-2 전체 흐름도

![매장 이용 흐름도](https://californialuv.github.io/Tech_Blog/images/2026-08-02/screen_golf_flow.png)
*스크린 골프 이용 흐름도*

고객이 매장을 방문하면 가장 처음 맞이하는 서비스들은 모두 내가 담당한 부분들이다.

1. 키오스크
2. 실시간 타석 룸 현황 보드 화면(DID)
3. 출입 인증 벽면 패드
4. 룸 이용 현황 패드

키오스크부터 벽면 패드는 고객이 방문하자마자 직접 사용하는 무인화 서비스 시작점이기 때문에 작은 오류 하나만 발생해도 매장 이용에 대한 신뢰도가 크게 떨어질 수 있다. 
그래서 단위 테스트는 물론, __유저 테스트__ 도 꼼꼼하게 준비했다.

특히 사용자 테스트는 IT 팀원들보다 실제 현장 매니저들이 고객의 입장에서 불편한 점이나 예상하지 못한 동작 오류를 더 잘 발견할 수 있다고 판단했다.
이에 무인화 설치가 예정될 각 직영점의 매니저들에게 Slack으로 이용 테스트를 부탁드렸다. (무인화 시공 전 기기들은 미리 각 직영점 창고에 이미 보관 중)

![매장 매니저 채팅](https://californialuv.github.io/Tech_Blog/images/2026-08-02/chat-1.png)
*키오스크 기기 매뉴얼 안내*

무작정 매니저들에게 정해진 순서대로 동작을 테스트 하도록 안내하는 방식은 적절하지 않다고 판단했다.

개발자나 기획자는 서비스를 직접 만들고 기획하는 과정에서 이미 많은 부분을 파악하고 있기 때문에 정해진 테스트 시나리오를 따라가면 금방 테스트 방식에 익숙해질 수 있지만
매니저들은 처음 접하는 서비스 기기인 만큼 오히려 사용 메뉴얼 자료를 보면서 자유롭게 사용해 보는 쪽이 더 적합해 보였다.

또한 이번 무인화 프로젝트는 기존 매니저들의 근무 형태와 인력 운영에도 영향을 주기에 기기 이용 테스트를 부탁드리는 과정에서도 체크 리스트 형태 같은 딱딱한 방식보단
최대한 예의를 갖추고 사용 메뉴얼 전달이 오히려 부담을 줄일 수 있기 때문에 신중하게 요청드릴 필요가 있었다.

그 결과, 실제 고객을 응대하는 현장 매니저들로부터 앱 내에서 예약 및 충전 등 사용법 안내 방식부터 연령대가 높은 고객을 위한 안내 문구 제안까지 다양한 피드백을 받았다.

## 2-3 APP / WEB 배포 과정

![배포 과정](https://californialuv.github.io/Tech_Blog/images/2026-08-02/app-web-deployment-process.png)
*키오스크 기기 매뉴얼 안내*

웹앱(WebView) 기반으로 운영되는 서비스이므로 배포는 APP과 WEB 두 갈래로 나뉜다.

APP 배포는 비교적 간단하다. KICC 개발팀에 APK 파일과 버전 정보(versionName, versionCode)를 전달하면, 앱 심사 후 KICC 측 Store 앱에서 앱을 등록해준다.

WEB 배포는 main 브랜치로 머지되면 Vercel에 자동 배포된다.

이때 APK는 빌드 시 환경 변수로 주입된 Vercel 배포 도메인을 WebView로 원격 로드한다. 
즉 APK는 네이티브 셸 역할만 하고, 실제 화면은 항상 Vercel의 최신 배포를 바라본다.

덕분에 네이티브 SDK 영역(키오스크 잠금, KICC 결제 연동 등)이 아닌 단순 화면 수정이나 API 연동 작업이라면,
KICC에 재배포를 요청하고 키오스크, 패드마다 재업데이트를 할 필요 없이 WEB 배포만으로 전 매장에 즉시 반영된다.

이 구조가 특히 중요한 이유는 운영 규모에 있다. 직영점만 수십 곳이고, 각 매장에 설치된 키오스크 패드까지 합치면 관리해야 할 기기가 수십 대에 이른다.
원격 로드 구조가 아니었다면 간단한 화면 수정 하나에도 매장 매니저들이 기기를 일일이 업데이트해야 했을텐데
__WEB 배포 한 번__ 으로 전 매장 기기에 동시 반영되므로, 매장 운영에 손을 대지 않고도 서비스를 개선할 수 있다.

A 이용자가 이용을 종료한 후 다음 이용자의 12:00 전까지 남은 5분이라는 자투리 시간 동안 정리를 하거나 조금 더 골프를 이용하는(?) 경우가 있다.
이때 5분 사이에 B 이용자가 벽면 패드에 전화번호를 입력하면 잠겨 있던 문이 열리면서 입장할 수 있어, A 이용자와 서로 난처한 상황이 발생하는 경우가 종종 나타난다고 하였다.

연예인들도 자주 방문할 만큼 프라이빗한 스크린 골프 이용 환경을 중요하게 생각하는 서비스였기에,
이용 고객끼리 서로 마주치는 상황은 단순한 불편을 넘어 서비스의 장점을 훼손할 수 있는 치명적인 문제였다.

현재 이용자와 다음 이용자가 입·퇴실 과정에서 서로 마주치는 상황을 방지하기 위해, 아래와 같은 규칙을 적용해 입장을 제한하기로 했다.

```
1. __현재 이용자가 있는 경우__, 다음 이용자의 예약 시간이 되기 전까지는 __'이용 중'__ 화면을 노출한다. 다음 이용자 이용 시작 1분 전인 __59분부터 '입장하기'__ 화면으로 전환한다.
2. __현재 이용자가 없는 경우,__ __'입장하기'__ 화면을 계속 노출한다. 다음 이용자가 예약 시작 전인 __55분에 전화번호 인증을 완료하더라도__, 즉시 __'이용 중'__ 화면으로 전환한다.
```
<br>

5분이라는 짧은 시간에도 입·퇴실 과정에서 여러 상황이 발생할 수 있었고, 이를 방지하기 위해 입장 규칙을 더 엄격히 적용해 문제를 해결했다.

### 아예 몰라요 아예

![아예 몰라요](https://californialuv.github.io/Tech_Blog/images/2026-08-02/idk.png)

직영점의 무인화 설치가 완료된 후에는 각 매장 계정에 Slack으로 기기 사용 방법이 담긴 매뉴얼 PDF를 개별적으로 안내했었다.그러나 여전히 기기 사용에 매니저들이 어려움을 겪는 일이 자주 일어났다. Slack 개인 메세지로 하나하나 설명하다 보면 나도 점점 답답해져
결국 전화로 직접 안내하는 경우도 많았고 사용법을 이해시키는 과정에서 시간과 에너지를 상당히 소모하기도 했다.
더 큰 문제는 어렵게 사용법을 알려드렸던 매니저가 퇴사한 뒤였다. 새로 채용된 매니저가 제대로 인수인계를 받지 못해 다시 나에게 사용법을 알려달라고 요청하는 '뫼비우스의 띠'가 반복되었다.

내가 직접 매니저들에게 계속해서 기기 사용법을 교육하는 것은 적절하지 않다고 생각했으며 이 부분은 팀장님에게도 현재 운영 방식에 문제가 있다는 의견을 전달했다.

논의 끝에 직급이 높은 서비스팀 실장님들이 키오스크와 패드 사용법 PDF를 관리하고 각 매장 매니저들에게 직접 교육하는 방식으로 변경했다.
이후 개발팀은 사용 중 해결하기 어려운 문제나 기기 고장 신고 등 상황에서만 대응하도록 역할 방향을 재정리했다.

### 큰 제약이 걸린 환불 과정

![아예 몰라요](https://californialuv.github.io/Tech_Blog/images/2026-08-02/idk.png)

무인화 운영과 VAN 결제 방식의 한계가 실제 환불 상황에서 드러나기 시작했다.

오후 시간대에는 매장 근무자 없이 무인으로 운영되는데 고객이 환불을 요청하더라도 본사에서 원격으로 바로 환불 처리할 수 있는 방법이 없다.

결국 고객과 별도로 다음 이용 날짜 시간을 조율해 매니저가 직접 대응해야만 환불 처리가 가능 했으며 당장 환불이 필요한 고객에게는 큰 불편성을 느꼈을 것이다.
그렇다고 해당 시간에 매니저가 다시 방문해 환불을 처리하는 것은 무인화의 취지와도 맞지 않았고, 운영 측면에서도 상당히 비효율적이었다.

이전부터 VAN 결제 방식의 환불 처리에 대한 문제점을 인지하고 있었지만, 실제 무인 매장에서 환불 상황을 겪어보니 __무인화 서비스에 VAN 결제 방식은 잘 맞지 않는다__는 것을 확실히 체감했다.

수수료가 더 부과되더라도 환불 처리 측면에서는 __PG 기반 결제 방식이 무인 환경에 더 적합__ 해 보였다.

해당 문제점을 팀장님과 이야기해보니, 이미 여러 결제 서비스 업체와 미팅을 진행했지만 우리 서비스는 키오스크와 패드에 사용될 앱을 __직접 커스터마이징__ 해 운영할 예정이라 PG 결제 서비스를 적용하는데 제약이 있었다고 한다. 
필요한 기능을 추가하려면 해당 업체의 개발팀에 따로 개발을 의뢰해야 하며 비용 리스크가 추가적으로 발생할 수도 있어, 자체 개발팀을 보유한 우리 회사 입장에서는 오히려 비효율적이었다고 하셨다.

아무리 생각해봐도 실물 카드가 있어야만 환불 처리가 가능한 VAN 방식의 한계로 인해 앞서 언급한 환불 문제를 당장 해결할 뚜렷한 방법은 없어 보였다.
우선 고객들 대부분 한 달에 여러 번 방문하는 단골 고객이 많은 만큼 환불이 필요한 상황에서는 매니저가 고객과 일정을 조율해 직접 응대하는 방식이 현재로서는 가장 현실적인 대안이다.

위 환불 문제를 겪으며 무인화 서비스는 개발보다, 사람이 하던 판단과 대응을 시스템으로 대체하는 과정이 더 어렵다는 것을 느끼게 되었다.

그동안 소프트웨어 중심으로 개발 업무를 해왔지만, 이번 프로젝트에서는 하드웨어와 서비스를 연동하는 것은 물론 직접 현장 시공까지 참여하면서 현장 운영에서 발생하는 다양한 고충과 변수들을 직접 경험할 수 있었다.
